# Long-horizon plan — v0.2.0 "Proven Release"

**Created:** 2026-11-03
**Owner:** hcsmedia / timfromhcs
**Starting point:** `41d21a9` (v0.1.0 development preview, branch `master`, no remote)
**Target:** v0.2.0, first release with a public Git remote, a green CI run, a live
Vercel deployment and a documented, reproducible verification record.

This plan is written to be executed, not admired. Every phase has a gate with a
command and a pass criterion. A phase that cannot pass its gate is *not* done,
regardless of how much code exists.

---

## 0. Rules of engagement

1. **Evidence over claims.** No item is marked done without a command output, a
   file path or a URL that another person can re-run.
2. **One change, one reason.** Each commit is a single logical step; docs and
   code that describe the same fact change together.
3. **Fail closed.** A feature that cannot be verified is reported as
   unavailable (with the reason), never simulated in the UI.
4. **No silent scope cuts.** If a phase slips, it is moved to the v0.3.0
   backlog with a note in `STATUS.md`, not quietly deleted.
5. **No version bump without a gate.** The version string changes only after
   G6 passes.

### Test-and-fix loop protocol

Used for every phase (max 3 iterations per failure; then the phase is blocked
and written down):

```text
LOOP(n):
  1. RED     reproduce the gap with the smallest test that fails
             (unit test, fixture, CLI invocation or Playwright assertion)
  2. PATCH   minimal change; no drive-by refactors
  3. FIXED?  run the narrowest suite that covers the change
  4. GREEN   run the full gate for the phase
  5. EVIDENCE append the command + result to the phase log in this file
```

Full local gate (`npm run verify` already chains typecheck → unit → Rust →
build → E2E; Python is separate):

```bash
npm run typecheck
npm test
npm run test:rust
npm run test:python
npm run test:e2e
npm audit --audit-level=low
```

`npm run fmt:check` is **not** part of the gate: the baseline tree does not pass
prettier, so a release-only reformat would be an unreviewable diff. A repo-wide
formatting pass is a v0.3.0 task with its own commit.

Loop stop rule: three consecutive failures on the same assertion means the
design is wrong, not the test. Revert to the last green commit and re-plan.

## 3. Definition of done for v0.2.0

A release is stable when **all** of the following are true:

- D1. `npm run verify` and `npm run test:python` pass on a clean checkout.
- D2. CI runs on GitHub for the release commit and every job is green.
- D3. The production bundle is deployed and smoke-tested at a public URL
  (HTTP 200, correct headers, studio boots, worker runs).
- D4. `CHANGELOG.md`, `README.md`, `STATUS.md`, `ROADMAP.md` describe only what
  is true at the tag, with counts copied from the G6 run.
- D5. A `v0.2.0` tag and GitHub release exist, pointing at the verified commit.
- D6. `main` contains the release commit and the working tree is clean.
- D7. Every new capability has a test that fails without it.

## 4. Work phases

### Phase A — Performance: reusable WASM buffers

**Why:** `STATUS.md` lists per-call WASM buffer allocation as in-progress work.
Each force evaluation currently allocates and frees seven buffers, and memory
growth invalidates views. MD calls this thousands of times.

**Design**

- Add an arena inside `instantiateWasmKernel`: one growable block of
  `hcs_alloc`'d regions, sized by atom count, reused when `n ≤ capacity`.
- Re-create typed-array views **after** every possible growth (allocation may
  grow linear memory; the existing comment already says this).
- Grow geometrically (×2) to amortise; never shrink.
- `dispose()` frees the arena; calling `energyForces` after `dispose()` throws a
  typed `WasmKernelError("disposed")`.
- Expose `arenaCapacityAtoms` and `allocationCount` on the kernel for tests and
  the benchmark note. No behaviour change in results.

**Tests (packages/wasm/test)**

1. Parity unchanged for 1, 32, 108 atoms (bit-identical to the CPU kernel).
2. Repeated calls with the same `n` reuse the arena (`allocationCount` constant).
3. Growing `n` reallocates once and stays correct afterwards.
4. Shrinking `n` reuses the larger block and stays correct.
5. Different structures/species between calls do not leak parameters.
6. After `dispose()`, calls throw; the kernel is not silently revived.

**Gate A:** `npm test -w @hcs-materials/wasm` green **and**
`npm run build:packages && node benchmarks/lj-benchmark.mjs` shows parity
ΔE/ΔF ≤ 1e-10, with the new timing recorded in
`benchmarks/results/v0.2.0.json`.

### Phase B — MCP simulation tool (approval-gated, bounded)

**Why:** `STATUS.md` and `ROADMAP.md` both list simulation tools over MCP as
blocked "until a stable job API is exposed". The Node CLI *is* the stable job
API. Expose it honestly, with a hard approval gate.

**Design**

- New tool `simulations_run` in `python/.../mcp_server.py`:
  - inputs: `spec`, `structure`, `out_dir` (relative), `approve` (must be
    literally `true`), optional `backend`.
  - refuses `approve != true` (`approval_required`), missing CLI
    (`sim_cli_unavailable`), paths outside the workspace, and any workload over
    the budget: ≤ 5 000 atoms for `md.run`, ≤ 20 000 for energy, steps ≤ 2 000.
  - runs `hcs-sim run --structure … --spec … --out <root>/<out_dir> --json`
    as a subprocess with no shell, a timeout, a scrubbed environment and the
    workspace as cwd; never passes user strings to a shell.
  - returns the CLI JSON summary plus the written record paths; never invents
    numbers if the CLI failed.
  - configurable via `--sim-cli` / `HCS_SIM_CLI`; default `hcs-sim`.
- `simulations_validate_spec` stays non-destructive and is documented as the
  cheap pre-check.

**Tests (python/hcs_materials/tests/test_mcp.py)**

1. `approve` missing → `approval_required`, no subprocess started.
2. Workload over budget → rejected with the limit in the message.
3. CLI missing → `sim_cli_unavailable` with install guidance.
4. Happy path against a stub executable that writes the expected JSON → result
   passthrough, paths inside the root.
5. Path traversal in `out_dir` → rejected.
6. Timeout → `sim_timeout`, no partial claim of success.

**Gate B:** `npm run test:python` green **and** a manual run against the real
built CLI (`node packages/cli/dist/index.js`) recorded in
`docs/plan/evidence/B-mcp-run.txt`.

### Phase C — Checkpoint/restart for MD

**Why:** `STATUS.md` next-task 3. Long NVE runs need a resumable record instead
of being restarted from scratch.

**Design**

- `runMd` gains an optional `initialState` (`positionsCartesian`, `velocities`,
  `step`) and always returns `finalVelocities` and `finalStep`.
- `hcs-sim` writes `checkpoint.json` for `md.run` when `--checkpoint-out` is
  given and accepts `--resume <checkpoint>` to continue to a new step count.
- Checkpoint schema: `{ schema_version, structure_hash, steps_completed,
  timestep_ps, seed, positions, velocities }`; a hash mismatch is refused.
- Provenance marks resumed runs (`resumed_from.steps_completed`).

**Tests**

1. 100 steps in one run vs 50 + resume 50 → identical final positions,
   velocities and total energy (≤ 1e-12 absolute).
2. Structure-hash mismatch → refused before any step.
3. Checkpoint round-trip through JSON → identical numbers.
4. `steps_completed + requested == target`, no off-by-one.

**Gate C:** unit tests green + CLI round-trip recorded in
`docs/plan/evidence/C-resume.txt`.

```text
G0 baseline ──► A (wasm arena) ──► B (mcp run) ──► C (checkpoint)
   │                                                   │
   └──────────────► D (CI/remote) ◄────────────────────┘
                        │
                        ▼
                   E (deploy) ──► F (docs/release) ──► G (merge main)
```

Stop and re-plan if: a gate fails three loops in a row, a change would require
weakening an existing scientific claim, or a platform blocker cannot be removed
within one retry window.
